## 1. Purpose and Scope

This document defines NICo's configurable credential, authentication, KMS, and
certificate-provider architecture. Vault/OpenBao remains a supported,
configurable production provider; existing sites are not required to migrate from it.
Deployments can instead select independent credential, KMS, authentication, and
certificate providers as those alternatives become qualified. The document
covers the three related epics:

- [Phase 1: credential storage](https://github.com/dsx-ai-factory/infra-controller/issues/195)
- [Phase 2: API authentication](https://github.com/dsx-ai-factory/infra-controller/issues/5199)
- [Phase 3: remaining key and certificate services](https://github.com/dsx-ai-factory/infra-controller/issues/5200)

The design is intentionally high level. The following subsystem designs
and operator contracts remain authoritative for their implementation:

- [PostgreSQL-backed secret storage](postgres-secrets/README.md)
- [Secrets-storage operator contract](../configuration/secrets-storage.md)
- [Credential sources](../configuration/credential-sources.md)
- [Node-auth bearer JWTs](machine-identity/node-auth-jwt.md)
- [Machine-identity JWT-SVIDs and signing-key storage](machine-identity/spiffe-svid-sdd.md)
- [DPU bootstrap CA trust](../dpu-management/dpu_configuration.md#bootstrap-ca-trust)
- [NVSwitch mTLS certificates](../../helm/README.md#nvswitch-mtls-certificates)
- [Admin client certificates](../../helm/PREREQUISITES.md#admin-client-certificates)
- [Admin-client mTLS lifecycle and authorization](https://github.com/dsx-ai-factory/infra-controller/blob/main/docs/manuals/nico-api-auth.md)
- [Certificate-provider separation implementation](https://github.com/dsx-ai-factory/infra-controller/pull/2881)

The three phases are tracking boundaries, not a requirement to implement each
part serially. Work can proceed in parallel where the dependencies in
[Section 4](#4-provider-enablement-and-optional-migration-order) permit it.

### 1.1 Goals

- Make Vault/OpenBao a configured provider rather than an unconditional runtime
  dependency, while keeping it supported for production sites.
- Provide a scoped KMIP client as the first independent external KEK provider
  alongside Vault/OpenBao Transit; preserve the provider boundary for future
  KMS or HSM implementations.
- Preserve credential confidentiality, machine identity, and existing RBAC
  semantics.
- Support optional provider changes at live sites, with explicit overlap and
  rollback paths where data or trust actually changes.
- Preserve the existing internal node, UFM, service-transport, optional DPU OTLP
  gateway server, and optional NVSwitch certificate authorities, trust chains,
  leaf certificates, and private keys when selecting the cert-manager PKI
  provider. In the reference deployment, cert-manager and Vault use the same CA
  certificate and signing key, so selecting cert-manager changes only the
  signing path and does not migrate the CA, trust, leaves, or private keys. The
  separate admin-credential option can replace its Vault-issued client
  credential as described in
  [Section 3.2](#32-phase-2-api-authentication).
- Keep storage, key custody, node authentication, and certificate issuance as
  separate provider boundaries.
- Fail clearly when the configured provider or node credential is unavailable;
  do not silently switch custody or trust providers.

### 1.2 Non-Goals

- Repeating the low-level designs linked above.
- Mandating provider changes at existing production sites. Sites may continue
  using Vault; provider selection and any subsequent migration are operator
  decisions.
- Replacing every API client's mTLS authentication with JWT. Phase 2 moves only
  Scout and DPU-agent machine authentication to bearer JWTs. The admin CLI has
  no JWT path and always authenticates with mTLS using a client certificate
  issued by an operator-managed Vault or external CA independent of the
  machine-authentication mechanism. Transport TLS and other certificate
  consumers also remain.
- Removing Scout and DPU-agent machine mTLS support. A JWT-capable deployment
  may disable that machine-client mTLS path, but it remains supported and is
  separate from the admin CLI's required mTLS path.
- Defining full measured-boot or runtime attestation for DPUs.

## 2. End-State Design Summary

| Phase | Completed state |
| :--- | :--- |
| 1 — credentials | `nico-api` credentials written through the API or generated by NICo are envelope-encrypted in PostgreSQL; credentials explicitly owned by local configuration can come from file, environment, or mounted-secret sources; `nico-api` credential consumers use the provider abstraction, with Vault access confined to configured providers |
| 2 — API authentication | Scout and DPU-agent can use short-lived bearer JWTs instead of machine mTLS while the admin CLI retains mTLS with an operator-managed Vault or external admin CA; existing principals and RBAC policy are preserved; machine mTLS remains available |
| 3 — keys and certificates | Vault/OpenBao Transit and qualified KMIP servers are selectable production KEK providers; machine-identity signing-key encryption uses the shared KMS-backed envelope; Vault PKI remains supported while cert-manager provides an independently selectable path for node, UFM, service-transport, optional DPU OTLP gateway server, and optional NVSwitch certificates without forced certificate rotation |

## 3. Target Architecture

The end state has four independent security boundaries:

1. PostgreSQL stores encrypted credential records. A configured
   Vault/OpenBao Transit or qualified KMIP provider owns the KEKs and performs
   DEK wrap and unwrap operations; the provider is selected explicitly.
2. Nodes sign their own short-lived authentication tokens with the private key
   corresponding to their node certificate. The API maps the verified
   certificate identity to the same machine principal used by the current RBAC
   policy. Vault PKI and cert-manager are supported certificate-provider
   choices.
3. Certificate issuance is selected independently from credential storage and
   KEK custody. Vault PKI remains supported. The cert-manager alternative uses
   the existing internal issuing CA and has two issuance paths:

   - Service-transport, the optional DPU OTLP gateway server certificate, and
     optional NVSwitch certificates remain declarative cert-manager
     `Certificate` resources with their existing Secret and mount contracts.
     The OTLP collector's client credential is the dynamic node certificate,
     not a separate declarative OTLP certificate.
   - Dynamic node and UFM certificates use a Rust provider. The provider creates
     each private key only in `nico-api` process memory and submits a CSR-only
     cert-manager `CertificateRequest`; the private key never enters a Kubernetes
     resource. A node certificate remains matched to its JWT-signing key and
     chains to the existing API trust anchor.
4. The admin CLI retains mTLS. Existing reference sites may retain their
   Vault-issued credential and legacy `site-root` issuer classifier. An optional
   external admin CA bundle is a separate validation input and is not used as
   cert-manager signing material. That bundle may anchor at the same root as
   internal trust, but its admin client leaves use a dedicated intermediate with
   a globally unique issuer CN; a shared or root CA CN is never added as the
   classifier for this independent path.

### 3.1 Phase 1: Credential Storage

The [PostgreSQL secret-storage design](postgres-secrets/README.md) is
authoritative for the credential journal, envelope encryption, Vault import,
KEK routing, re-wrap, migration, and rollback mechanics. The
[Secrets Storage](../configuration/secrets-storage.md) and
[Credential Sources](../configuration/credential-sources.md) pages define the
operator-facing persistent and local-source contracts.

At the end of Phase 1, every `nico-api` credential consumer uses the
credential-provider abstraction. Credentials written through the API or
generated by NICo use envelope-encrypted PostgreSQL storage. Credentials
explicitly owned by local configuration use the documented environment, file,
or mounted-Secret sources. A provider that is not configured is not
constructed, so a configuration that does not select Vault does not create a
Vault client.
Phase 3 extends provider selection to credential consumers outside `nico-api`.

The site-wide BMC root has one cross-phase exception: a local source may
establish credential version 0 for initial DPF ingestion, but later versions
come from the persistent backend through coordinated rotation. Per-DPU Secret
delivery reuses the existing per-BMC credentials and rotation mechanism, as
described in [DPF BMC credential delivery](#dpf-bmc-credential-delivery) and
tracked by [#5958](https://github.com/dsx-ai-factory/infra-controller/issues/5958)
and [#6147](https://github.com/dsx-ai-factory/infra-controller/issues/6147).

### 3.2 Phase 2: API Authentication

Phase 2 changes machine-client authentication for Scout and DPU-agent: bearer
JWT becomes an alternative to machine mTLS while preserving their existing
principals and RBAC authorization boundaries. The admin CLI is tracked by
[#5199](https://github.com/dsx-ai-factory/infra-controller/issues/5199) only for
its separate certificate lifecycle. It is not part of the JWT transition or
machine-mTLS disablement and always uses mTLS; a site may retain its
Vault-issued CLI credential or configure the independent admin CA described
below.

#### Scout and DPU-agent

Scout and DPU-agent authenticate to the API with the bearer-JWT model defined by
[Node-auth bearer JWTs](machine-identity/node-auth-jwt.md). The token format,
short lifetime, API validation, machine-principal mapping, and RBAC behavior are
unchanged. Nodes re-mint tokens locally as expiration approaches; there is no
server-side token issuance or refresh RPC.

The required end state retains the credential model implemented by
[#355](https://github.com/dsx-ai-factory/infra-controller/issues/355):

- Scout and DPU-agent sign locally with the private key of the machine mTLS
  certificate. The certificate chain accompanies the JWT for API validation.
- The current node certificate and key remain valid through any provider
  cutover. A site may keep the Vault-backed provider. When cert-manager is
  selected, normal renewal or replacement generates an ECDSA P-256 key in
  `nico-api` process memory and submits only a CSR through a
  `CertificateRequest` to the same API-accepted trust anchor. That path retains the
  current digital-signature, key-agreement, key-encipherment, client-auth, and
  server-auth usages and the machine SPIFFE URI SAN. The provider validates the
  returned chain against that key before the
  existing API response delivers the credential to the node. It does not create
  a cert-manager `Certificate` or a Kubernetes Secret for this dynamic path, so
  the private key is not copied into cluster etcd or backups. This preserves the
  ES256-only JWT minter and validator contract and the key-custody boundary in
  the authoritative node-auth design.
- Normal renewal uses the existing machine-certificate response and node
  installation contract. Provider selection does not itself replace an
  installed certificate or key.
- Certificate issuance binds the public key to the intended machine identity;
  a valid chain alone is not sufficient to assert an arbitrary machine
  principal. The API continues to map the verified identity to the existing
  RBAC principal.
- Token lifetime, audience checks, TLS transport, and the dual-auth migration
  gate remain as designed in the completed JWT work.
- Machine mTLS remains supported for backward compatibility for as long as a
  deployment needs it. A site disables it only after every supported Scout and
  DPU-agent path can mint and locally re-mint tokens and replace and recover the
  selected signing credential and certificate, and after the API can disable or
  revoke one compromised signing credential without rotating the CA.

#### Admin CLI

The admin CLI retains its existing mTLS mechanism. Existing reference sites can
keep their Vault-issued credential and the legacy `site-root` issuer classifier.
A site may instead add an independently managed admin CA or rotation bundle to
the separate API admin trust configuration. For that independent path, a
dedicated admin-client intermediate issues the leaf certificate, and only that
intermediate's globally unique Subject CN is added as the admin issuer identity;
a shared or root CA CN is not added for the new path. A migration can overlap
the legacy and independent issuer identities until every old CLI credential is
retired, then remove the legacy classifier. The CLI does not require JWT
support. The existing
[admin client certificate contract](../../helm/PREREQUISITES.md#admin-client-certificates)
defines the configuration and its trust-boundary constraints.
Issuance, installation, renewal, recovery, and the existing revocation support
boundary are covered by the
[admin-client mTLS guide](https://github.com/dsx-ai-factory/infra-controller/blob/main/docs/manuals/nico-api-auth.md), completed in
[#7057](https://github.com/dsx-ai-factory/infra-controller/pull/7057).

### 3.3 Phase 3: Configurable Key and Certificate Services

#### Production KMS providers

The KMS interface supports multiple named providers, with one active provider
for new wraps and every configured provider available to unwrap the KEKs it
owns. Vault/OpenBao Transit remains a supported production provider. The first
independent external implementation is a deliberately scoped KMIP client rather
than a general-purpose KMIP SDK.

The KMIP provider maps each NICo `kek_id` to an operator-created, active KMIP
symmetric-key identifier. NICo generates a 256-bit DEK locally, sends only that
DEK to the KMIP `Encrypt` operation, and stores the returned ciphertext,
IV/nonce, and authentication tag in a versioned provider-owned encoding. Unwrap
uses the corresponding `Decrypt` operation. The KEK is non-exportable and never
enters NICo configuration or process memory. The provider uses mutually
authenticated TLS, validates the server identity against an explicit CA bundle,
and obtains its client certificate and key from mounted files rather than inline
configuration.

The supported KMIP subset is intentionally narrow: negotiated KMIP 1.4 or later,
the OASIS Basic Cryptographic Client operations, single-part `Encrypt` and
`Decrypt`, a 32-byte plaintext DEK, and an authenticated AES mode with a
server-generated IV/nonce. Startup validates protocol and operation support,
the configured object identifier, active state, key algorithm, key length, and
Encrypt/Decrypt usage. A server is supported only after the same wrap, unwrap,
restart, failover, key-disable, and error-mapping tests pass against that
product; claiming general KMIP compliance is not sufficient. The
[OASIS KMIP specification](https://docs.oasis-open.org/kmip/kmip-spec/v2.1/kmip-spec-v2.1.html)
defines the operation and response fields, and the
[KMIP profiles](https://docs.oasis-open.org/kmip/kmip-profiles/v2.1/kmip-profiles-v2.1.html)
define the cryptographic client and server conformance boundaries.

The provider does not create, activate, rotate, revoke, or destroy KEKs. Those
remain operator-controlled KMS lifecycle operations. NICo rotation creates a new
`kek_id` mapping, routes new wraps to it, and re-wraps existing DEKs while the old
key remains available through the rollback and backup-retention windows. The
initial supported KMIP products and their exact interoperable protocol and
cryptographic profiles must be recorded when the provider is qualified.

Barbican is not part of this KEK path. Its
[public interface](https://docs.openstack.org/barbican/latest/api/reference/secrets.html)
stores and returns secret payloads, while its KMIP integration is an internal
secret-store plugin. A future Barbican integration would therefore be a
credential-store provider, not this KMS provider; the scoped NICo KMIP client
connects directly to the operator's KMIP service.

The Integrated provider's key sources and their production restrictions are
defined in [Secrets Storage](../configuration/secrets-storage.md). A mounted-key
Integrated deployment receives the same production qualification for custody,
availability, rotation, and recovery as an external provider.

Provider migration reuses the existing multi-provider, routing, and re-wrap
behavior. A site can keep Transit as its active provider indefinitely. If it
selects KMIP, new DEKs are wrapped by the KMIP provider while Transit remains
available to unwrap old records. If a site chooses to retire a superseded KMS
provider, all records must first be re-wrapped, recovery tested, and the rollback
window ended; no retained backup within the restore window may still require it.

#### cert-manager-backed certificate provider

The reference installation creates the `site-root` CA and direct
`site-issuer` with cert-manager before Vault starts, then imports the same CA
certificate and signing key into Vault PKI. The direct issuer and
`vault-nico-issuer` are different resource paths to the same cryptographic
issuer. Vault PKI remains supported; direct cert-manager issuance is an
independently selectable path.

A new Rust crate, patterned after
[`carbide-dpf`](../../crates/dpf/README.md), encapsulates cert-manager
Kubernetes resources behind a narrow interface. Its `CertificateProvider`
implementation handles dynamic node and UFM issuance. For each request, it:

- generates an ECDSA P-256 private key only in `nico-api` process memory;
- submits the public key in a CSR-only, namespaced `CertificateRequest`;
- observes approval, issuance, or failure;
- validates that the returned certificate matches the key, requested identity,
  and profile;
- returns the existing `CertificateProvider` result; and
- cleans up the request.

The provider does not create a cert-manager `Certificate` or Kubernetes Secret
for a dynamic credential, so the private key never enters cluster etcd or its
backups. A node credential is returned through the existing
machine-certificate API response. UFM retains the existing manual handoff:
`CreateCredential` stages the CA and certificate plus a mode-`0600` key file
in the `nico-api` pod for the operator to install. If the files are lost before
installation, the operator repeats issuance; the staged key is removed after
installation is verified.

The current identities, SANs, usages, algorithms, and lifetime limits remain
unchanged. Approval policy, CSR-profile enforcement, and least-privilege RBAC
must cover the dynamic provider before it is selectable. These are issuance
security requirements, not certificate-migration steps.

Service-transport and optional NVSwitch certificates retain their existing
cert-manager `Certificate` resources, Kubernetes Secrets, mounts, identities,
and profiles. When direct issuance is selected, it uses the existing
`site-root`. The optional DPU OTLP gateway certificate already uses the direct
`site-issuer` and does not change; its DPU client credential remains the
dynamic node certificate.

For an existing reference site, provider selection verifies that the direct
issuer uses the same CA certificate and signing key as Vault PKI. If they match,
normal Helm and application configuration select the direct issuer and dynamic
provider. Existing CA trust, leaves, private keys, Secrets, and mounts remain
unchanged; existing leaves continue until normal renewal. If they do not match,
the site remains on Vault PKI and a custom CA migration requires a separate
design. A new site choosing direct issuance configures that issuer in its
initial Helm configuration, independently of its credential and KMS choices.

Selecting cert-manager does not construct a certificate-issuance Vault client,
although independently selected credential or KMS providers may still use
Vault. It is not a CA upgrade or rollover. Future CA lifecycle and recovery use
the same support level as today and are outside this provider-selection design.
API-side enforcement of individual node credential disablement or revocation
remains an open requirement tracked by
[#5956](https://github.com/dsx-ai-factory/infra-controller/issues/5956).

#### Encryption convergence

Machine-identity signing-key encryption uses the same KMS-backed envelope
primitive as credential storage. The machine-identity data model and behavior
remain defined by the [JWT-SVID design](machine-identity/spiffe-svid-sdd.md);
only encryption and KEK custody converge. Each subsystem retains its own storage
while using per-record DEKs wrapped by the configured production KEK provider.

#### DPF BMC credential delivery

NICo already maintains per-BMC credentials and has a
[BMC credential rotation mechanism](../../crates/credential-rotation/src/lib.rs).
DPF credential delivery reuses those records and that mechanism.

`nico-api` derives a namespace-local Secret for each DPU through the existing
credential-manager abstraction and references it from
`DPUDevice.spec.bmcCredentialSecretName`. The Secret's `password` key reflects
the credential confirmed on that device rather than the latest site-wide
target. This keeps DPF access valid while devices use different credential
versions.

The integration reconciles these Secrets after retries or restarts and
coordinates credential changes with DPF so dependent operations use the
matching password. DPF must support consuming credential updates safely before
rotation is enabled for DPF-managed devices. Qualification and integration are
tracked by [#6147](https://github.com/dsx-ai-factory/infra-controller/issues/6147);
the supporting DPF behavior remains a prerequisite.

Initial version-0 bootstrap retains the
[Credential Sources](../configuration/credential-sources.md) contract;
version 1 and later use the persistent backend. Derived Secrets have
least-privilege access and are cleaned up with their device references. DPF
reads those Secrets and receives no direct access to credential files,
PostgreSQL, or rotation bookkeeping.

## 4. Provider Enablement and Optional Migration Order

1. **Adopt the phase-1 provider chain.** Enable the provider abstraction and
   PostgreSQL credential backend. A site may keep Vault first in its read chain
   and as its writer, or import existing secrets and make PostgreSQL
   authoritative while retaining Vault read fallback until every required
   credential has been verified.
2. **Make services outside `nico-api` provider-aware.**
   `dsx-exchange-consumer` reads credentials from its configured environment,
   file, mounted Secret, or Vault source, and constructs its Vault reader only
   when configured. Persistent `powershelf-manager` and `nvswitch-manager`
   deployments select their credential backend explicitly. `bmc-proxy` and
   `machine-a-tron` charts omit unused credential-service settings while
   preserving TLS configuration for the selected Vault-backed or direct issuer.
   On a site with a predecessor Flow deployment, setup stops
   before mutation while PSM or NSM containers remain. After the operator moves
   any site-specific manager dependencies and upgrades and verifies the
   Flow-only release, rerun setup with the legacy Vault available to revoke
   obsolete PSM/NSM tokens and clean up their policies, Secrets, and RBAC, while
   preserving configured Vault providers.
3. **Enable independent API authentication.** Run Scout and DPU-agent bearer JWTs and
   machine mTLS in parallel and verify that both produce the same principals and
   authorization results. A site may retain its Vault-issued admin CLI
   certificate. If it selects an independent admin CA, add that CA to API trust,
   issue and install the new CLI certificate, stage it alongside the
   Vault-issued credential, and preserve the existing admin authorization
   boundary.
4. **Configure the production KMS provider.** Keep Vault/OpenBao Transit active,
   or configure and qualify the KMIP provider. A site migrating to KMIP routes
   new wraps to it, retains Transit for old records, re-wraps, and tests
   recovery. Keep both providers configured through the defined rollback and
   backup-retention windows; the rollback procedure is defined in
   [Secrets Storage](../configuration/secrets-storage.md).
5. **Optionally select the cert-manager-backed certificate provider.** A site
   can retain Vault PKI. An existing reference site verifies that the direct
   issuer uses the same `site-root` certificate and signing key as Vault PKI,
   installs the Kubernetes-resource abstraction and required issuance policy and
   RBAC, then selects the direct issuer and dynamic provider through normal Helm
   and application configuration. Existing CA trust, certificates, keys,
   Secrets, and mounts do not change; existing leaves continue until normal
   renewal. A mismatch leaves Vault PKI selected. A new site choosing
   cert-manager configures the direct issuer in its initial Helm configuration.
   Enable individual node-credential revocation or disablement before relying
   on JWT as the only
   machine-authentication path. This selection does not change any Vault
   credential or Transit provider configured by the site.
6. **Integrate per-DPU BMC credential delivery.** Adopt and validate supporting
   DPF behavior, reconcile per-DPU Secrets from existing per-BMC credentials,
   and attach their references to `DPUDevice` resources. Verify safe handoff
   during rotation, restart, and failure recovery before enabling BMC rotation
   on DPF-managed devices. The existing shared-Secret bootstrap remains
   supported while [#6147](https://github.com/dsx-ai-factory/infra-controller/issues/6147)
   is pending.
7. **Make installation provider-driven.** `helm-prereqs` phases and chart
   defaults deploy the Vault AppRole and token Secrets, `vault-cluster-info`
   ConfigMap, and Vault-backed issuer only when a selected provider requires
   them. New and existing sites may select Vault for credentials, Transit, PKI,
   or any combination. A site using only independent providers can omit Vault.
   DPF initializes in the initial Core rollout. An operator may supply
   version 0 through the local environment/file chain, including a watched
   Secret, or populate a configured persistent backend through the normal
   credential API. Local startup requirements and source precedence remain
   defined by [Credential Sources](../configuration/credential-sources.md).
   New DPU registration waits for credential delivery. The local path needs no
   admin credential; the API path uses the operator's normal admin mTLS
   credential. Neither path requires an installer-created temporary
   credential, an in-cluster CLI job, or a second Core rollout.
8. **Verify each selected provider combination.** Prove startup, steady-state
   operation, rotation, backup restore, rollback, and failure recovery for the
   configured credential, KMS, authentication, and PKI providers. A deployment
   that selects Vault verifies those paths; a deployment that omits Vault proves
   operation with Vault unavailable.
9. **Converge machine-identity encryption.** After either production Transit or
   KMIP KEK provider is available, move machine-identity signing-key encryption
   to the shared envelope primitive. This completes the shared KEK-custody model
   without requiring a provider migration.

Steps 4 and 5 can be developed and selected independently. KMS-provider
migration uses the re-wrap and overlap procedure above. Selecting the same-CA
cert-manager path changes certificate issuance configuration without a CA or
trust migration. Step 6 can proceed independently of those provider choices;
BMC rotation on DPF-managed devices remains unsupported until its integration
is qualified. For a new site omitting Vault, step 7 depends on the applicable
independent-provider work in steps 2 through 5. Provider-driven installation
in step 7 can retain the shared-Secret bootstrap while per-DPU delivery
(step 6) is pending. DPF BMC bootstrap does not
introduce an admin CLI dependency. Step 8 validates the combination selected
by the operator; existing Vault-backed combinations remain supported. Step 9
depends on step 4 but can otherwise proceed independently.

## 5. Failure, Security, and Availability Boundaries

- Vault is contacted only when a configured credential, Transit, or PKI
  provider requires it. A deployment that does not select Vault never silently
  reconnects to it.
- Loss of a node signing key or certificate prevents new JWTs and, when the same
  credential is used for mTLS, also prevents machine mTLS. The selected
  certificate lifecycle therefore defines renewal, replacement, revocation,
  and recovery.
- The certificate enrollment authority must bind each approved public key and
  identity to the intended inventory record. Before a deployment elects to
  disable Scout and DPU-agent machine mTLS as a fallback authentication path,
  the API validation path enforces individual credential disablement or
  revocation through the CRL, OCSP, denylist, or equivalent mechanism selected by
  [#5956](https://github.com/dsx-ai-factory/infra-controller/issues/5956).
  This option does not affect the admin CLI's required mTLS authentication.
  Issuance-side revocation without validation enforcement does not meet this
  requirement. The selected design also provides a compromise recovery
  procedure.
- A previous KMS provider remains available until no live record and no retained
  backup within the restore window references it, and until the rollback window
  ends. Re-wrap is resumable and does not change credential plaintext.
- Credential reads synchronously unwrap DEKs through the KEK provider, so an
  external KMS outage fails affected credential operations, and an Integrated
  provider whose mounted key is unavailable cannot restart or scale out while
  already-running instances continue. Runtime availability, startup
  availability, rotation by controlled restart, and recovery are therefore part
  of provider qualification. Provider mechanics are defined in
  [Secrets Storage](../configuration/secrets-storage.md) and the
  [PostgreSQL secret-storage design](postgres-secrets/README.md).
- The KMIP provider never retrieves or exports a KEK. Its mTLS identity is
  scoped to Encrypt, Decrypt, Query, and attribute-read operations for the
  configured key objects. A KMIP outage has the same synchronous read impact as
  a Transit outage. The provider's versioned encoding preserves every response
  field needed for authenticated decryption, and interoperability tests prove
  that encoding and error behavior against every supported server product.
- On an existing reference site, direct cert-manager selection requires the
  same CA certificate and signing key as Vault PKI. A mismatch fails before
  selection and leaves Vault PKI active; custom CA migration is outside this
  design. A new site choosing direct issuance selects that issuer in its
  initial configuration.
- Approval policy, CSR-profile enforcement, and least-privilege RBAC protect the
  dynamic `CertificateRequest` path before it is selectable.
- Dynamic node and UFM `CertificateRequest` resources contain CSRs and signed
  certificate material, never private keys; the provider creates no certificate
  Secret. Node keys remain in process memory until returned through the existing
  API response. UFM keys leave process memory only for the restricted, pod-local
  manual handoff and are removed after verified installation.
- Provider selection does not change CA trust, existing leaves, private keys,
  Secrets, or mounts. Future CA rollover and compromise recovery remain separate
  lifecycle concerns at the same support level as today.
- Credential plaintext, private keys, and bearer tokens are never logged.
  Production KEKs remain in Vault/OpenBao Transit or a qualified KMIP server. A
  mounted-key Integrated provider requires separate production qualification;
  [Secrets Storage](../configuration/secrets-storage.md) defines why inline key
  material is limited to development and test.
- The operator-managed local BMC credential chain owns only version 0, with the
  environment source ahead of the watched file. Once a managed device uses
  that value, changing the local source is not a supported hardware rotation;
  version 1 and later stay in the persistent backend. Local credential Secrets
  and DPF's derived per-device Secrets are namespace-local and independently
  access-controlled. Production deployments require encryption at rest for
  credential Secrets and encrypted, access-controlled backups with audited
  access and documented retention. Each `DPUDevice` references the credential confirmed on
  that device, and DPF credential updates must be qualified before rotation is
  enabled for DPF-managed devices.
- Provider credentials use workload identity or mounted secret sources where
  supported and are independently rotatable from the data they protect.
- Multi-replica NICo deployments use shared PostgreSQL state and highly
  available KMS and CA endpoints; no replica owns unique recovery material.

## 6. Completion Criteria

The overall effort is complete when a supported site can:

- select Vault-backed or independent providers explicitly through configuration
  without changing application code;
- install and operate with Vault/OpenBao where any selected provider requires
  it, or omit Vault when every selected provider is independent;
- read, write, rotate, back up, and restore credentials using PostgreSQL with
  either Vault/OpenBao Transit or a qualified KMIP server as the production KEK
  provider;
- preserve DPF Redfish access to every registered DPU while coordinated BMC
  rotation leaves the fleet on mixed credential versions;
- bootstrap and authenticate Scout and DPU-agent, locally re-mint their tokens,
  and rotate, revoke, or recover their signing credentials through the selected
  Vault-PKI or cert-manager provider;
- authenticate the admin CLI with its existing Vault-issued certificate or an
  independently issued mTLS credential while preserving its authorization
  boundary;
- retain Vault PKI or select cert-manager to issue and normally renew every
  node, UFM, service-transport, optional DPU OTLP gateway server, and optional
  NVSwitch certificate with the existing identity, SAN, usage, algorithm, and
  lifetime contracts, without forcing provider-selection-time CA, leaf, or
  private-key rotation; the DPU OTLP client continues to use the node
  certificate;
- issue dynamic node and UFM certificates without storing their private keys in
  Kubernetes Secrets or cluster etcd, and remove the staged UFM key after
  verified installation;
- verify that the direct issuer and active Vault PKI issuer use the same CA
  certificate and signing key before selecting cert-manager on an existing site,
  and leave a custom site on Vault when they do not match;
- select Vault PKI or the direct issuer in a new site's initial configuration;
- enforce approved certificate profiles and least-privilege access on every
  cert-manager request path;
- preserve existing CA trust, leaves, private keys, Secrets, and mounts when
  selecting the same-CA cert-manager path, without forced rotation or
  reissuance;
- preserve machine identity and RBAC behavior through migration;
- optionally change credential, KMS, or PKI providers without credential loss
  or interruption of authentication; Vault-backed combinations remain supported;
- demonstrate rollback at every credential or KEK provider-overlap stage and
  prove the same-CA cert-manager path before selecting direct signing; and
- protect machine-identity signing keys with the shared envelope and the
  configured production KEK provider.

## 7. Open Questions

1. Which KMIP server products and exact protocol and cryptographic profiles are
   qualified first, and what are the minimum supported high-availability,
   backup, and recovery configurations? This decision is tracked by
   [#3253](https://github.com/dsx-ai-factory/infra-controller/issues/3253).
2. How does API validation enforce individual node signing-credential
   disablement or revocation before certificate expiry without a CA-wide
   rotation? The same-CA cert-manager provider and new Rust
   Kubernetes-resource abstraction are selected; request naming, cleanup, and
   retry mechanics remain implementation details. The validation decision is
   tracked by
   [#5956](https://github.com/dsx-ai-factory/infra-controller/issues/5956).
3. Does `dsx-exchange-consumer` require live credential reload, or is rotation
   by restart sufficient? This decision is tracked by
   [#5957](https://github.com/dsx-ai-factory/infra-controller/issues/5957).
4. What configuration selects each credential, KMS, and PKI provider, and what
   invalid or conflicting combinations fail startup? What upgrade and rollback
   window remains supported? This
   decision is tracked by
   [#5958](https://github.com/dsx-ai-factory/infra-controller/issues/5958).
5. Which DPF release and API safely consume per-device credential updates,
   and how does NICo verify that DPF uses the updated credential before
   allowing dependent operations? This decision is tracked by
   [#6147](https://github.com/dsx-ai-factory/infra-controller/issues/6147).
